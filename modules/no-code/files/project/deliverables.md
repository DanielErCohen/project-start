# Deliverables

A deliverable is anything that leaves the project for a client, customer or audience: a playbook, template, price list, report, checklist or published page.

> ADAPT: list this project's real deliverables; keep only the wording rules {{OWNER}} requires.

## Filing

- One file or folder per deliverable, named `YYYY-MM-DD-topic-v1.md`. The version rises only when a sent copy changes.
- The drafting copy lives here. The sent copy lives where the client reads it, and the register records where.
- Binary files stay out of git; the register holds their location.

## Sign-off

This sign-off is the merge-mode equivalent for a project without code: nothing is sent until it is done.

1. The agent drafts and checks the draft against the brief and the wording rules.
2. {{OWNER}} answers approve or change. Nothing reaches a client without that answer, because a sent message cannot be recalled.
3. Where the client must approve each item (a contract, a regulated field, a partner), the item waits for the client's written yes, and the register records the date.
4. The agent records the date and version. A later change is a new version and the old row stays.

## Wording rules

- Plain words and short sentences in the client's own terms, with no internal names or codes.
- No promise the project does not control (outcomes, dates, prices) unless {{OWNER}} wrote it.
- A client's personal data appears only in material for that client. Names and amounts are checked against the source.
- One recommendation per decision asked of the reader, with a default.
