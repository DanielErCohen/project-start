# Principles

The reasoning behind the core files and the modules. Each section gives the rule, the reason, and for contested choices the public sources with the date each was read or published. Sources checked 2026-10-26; "undated" means the page shows no date.

## Owner and decisions

**The owner decides what only the owner can decide.** Product scope, spend, go-live, anything that reaches other people, irreversible actions and the owner's own accounts sit with the owner. Claude decides technical points and records them in one line with the reason. Reason: every wait on the owner stalls the project.

**Questions arrive one at a time with a default.** The agent proceeds on the default until the owner answers, so no question blocks work. `owner.md` holds only items blocked on the owner, each expanded into every step. Reason: a list mixed with engineering decisions cannot be cleared in one sitting, and an item that sends the owner back to ask for steps wastes the owner's attention.

**Merge and deploy are separate decisions.** Four merge modes: solo (the owner pushes the default branch directly and reviews the unpushed commits first), orchestrator (Claude merges when checks and review pass), human-review (a named person approves) and issues-only (a partner owns the code and the output is issues). An agent review never counts as the human review. Reason: a merge to the main branch can apply migrations at once while the code goes live later, so one yes cannot cover both.

**The decision log is never rewritten.** `decisions.md` records costly-to-reverse decisions and stop lines with the date, the reason and what would change them. A changed line adds an entry. Open questions carry their default, and deferred items carry their reason. Every other file states the current position, with history in git. Reason: git shows what changed and not why at the time, and without a log decided items get raised again. Sources: [adr.github.io](https://adr.github.io/) (undated) treats the set of records as the decision log, and [Thoughtworks Radar](https://www.thoughtworks.com/radar/techniques/lightweight-architecture-decision-records) rated them Adopt (last updated 2018-05-15). No recent source compares records with a dated log, so the dated log is a judgement.

## Evidence

**A claim carries a stage, a unit, a date and a basis.** The stages are proposed, delivered, reported, measured and verified. Rates are written as counts first, and "never happens" needs a query built to detect the thing. Reason: with few participants one person moves a rate by many points, and an absence in the data may be an absence of the instrument.

**Kill lines come first and come from the user's need.** A kill line is written before the test, with a read date and a decision for each outcome. It is never set from a past best score. The agent checks that the data for the test exists before scheduling it. "Not measured" never counts as passing, and a failed line triggers a decision to stop, pivot or rescope. It never triggers a new metric. Reason: criteria written after the data are fitted to the data, a bar anchored to a past best measures the old system, and a bar moved after a miss stops being a bar. Sources: [Eppo, 2025-01-27](https://geteppo.com/blog/make-decisions-before-experimenting) describes deciding before experimenting and notes that five metrics with three states each give 243 outcome combinations, which is why a card carries one primary metric and at most two guardrails. [Kohavi et al., arXiv 1801.08532](https://arxiv.org/pdf/1801.08532) says long-term holdouts need a specific learning goal. A holdout of 5 to 10 percent for four weeks is a practitioner rule I could not confirm in a primary source, so the card asks for a size and a purpose and gives no default.

**Empty, failed and degraded are three results.** A pipeline checks its output count, and a null from an outage is never read as an answer. Reason: a run that did nothing reports success unless something counts its output.

**Money has one source of truth.** The payment processor is the reference, and the reconciliation difference reads zero before a report or tax use. Reason: a "paid" status in the app does not prove the money arrived.

**Promises and public claims map to code.** Each published promise points to the code or runbook that keeps it, and each public claim is checked against the code. When they differ the owner chooses which changes. Reason: a promise resting on one inbox fails when the person is away, and copy that promises a behaviour the code lacks is a defect users find first.

## One agent and fresh review

**Single agent by default.** The main session plans and codes. Subagents handle read-only recon and independent slices, and an editing subagent runs with `isolation: worktree`. Reason: coding tasks hold shared decisions, and parallel agents make conflicting ones. Sources: [Anthropic, 2025-06-13](https://www.anthropic.com/engineering/multi-agent-research-system) found multi-agent research beat a single agent by 90.2 percent on an internal research evaluation at about 15 times the tokens, and says most coding tasks have fewer parallelizable parts than research. [Google Research, 2026-01-28](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/) tested 180 configurations: every multi-agent variant cut performance on sequential tasks by 39 to 70 percent, and independent agents amplified errors 17.2 times against 4.4 times with central coordination. [Cognition, 2025-06-12](https://cognition.com/blog/dont-build-multi-agents) advises a single-threaded linear agent and expects that to change. The evidence favours parallelism for research more than for coding.

**Review runs in a fresh context.** `/code-review` runs after the checks pass. Reason: the Claude Code documentation says a fresh context will not be biased toward code it just wrote, though it gives no measurement. [Panickssery et al., 2024](https://arxiv.org/pdf/2404.13076) found evaluators favour their own output, and [Wataoka et al., 2024-10-29](https://arxiv.org/abs/2410.21819) tie the bias to familiar text.

**A second model family is for risk classes.** Payments, sign-in, personal data, storage and migrations add `/security-review` and one review by a different model family or by a human with domain knowledge. Routine work does not. Reason: the newest test is thin. A single-author preprint, [arXiv 2610.01471, 2026-10-01](https://arxiv.org/abs/2610.01471), found a cross-family reviewer not significantly different in F1 from a fresh same-model session, found that the two catch partly different errors, and found one of each caught more planted errors than two same-model reviews. It is not peer reviewed. [arXiv 2607.21656, 2026-07-22](https://arxiv.org/abs/2607.21656) reports an asymmetric pairing. No controlled study compares a fresh same-model session with another family on the same coding review tasks, so this is a recommendation and the owner may choose otherwise.

**One review round, a second only to re-check a fix, stop at two.** Reason: [Huang et al., ICLR 2024](https://arxiv.org/pdf/2310.01798) found models did not reliably fix reasoning without outside feedback, though those were 2023 models. The Claude Code documentation notes a reviewer will usually report some gaps even when the work is sound, so the review is told to flag correctness and requirement gaps only.

**Fresh agent or the author for a fix.** The author fixes while its context is small and recent, and a fresh agent fixes otherwise. Reason: [Chroma, 2025-07-14](https://research.trychroma.com/context-rot) found reliability falls as input grows, and [Anthropic, 2025-09-29](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) calls context a finite resource with diminishing returns.

## Models and effort

**Models are named in one dated table, plus the fields that set them.** As of October 2026: Opus 5.5 at medium effort for orchestration and coding, high for hard work; Haiku 5.5 for recon and checkable subtasks; Sonnet 5.5 for cost-bounded parallel or routine work; Fable 5.1 only by explicit escalation. Roles come from Anthropic's [models overview](https://platform.claude.com/docs/en/models/overview) (undated) and [Haiku 5.5 launch](https://www.anthropic.com/claude-haiku-5-5) (2026-10-07). The vendor says Opus 5.5 performs at the level of Fable 5.1 on most work ([launch, 2026-09-22](https://www.anthropic.com/news/claude-opus-5-5)), which I did not measure. In the vendor's own test an Opus executor with a Fable advisor gained 1.7 points at about 2.1 times the cost, "at the edge of run-to-run noise" ([cost and intelligence guide](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence), measurement dates not stated). The table in `working-agreement.md` carries the date. The only other places that name a model are agent definitions and skills that set a `model` field, so a model change touches the table, those fields and those skills.

**Set `model` and `effort` in each agent definition.** Effort is a behavioural signal and not a token budget ([effort](https://platform.claude.com/docs/en/build-with-claude/effort), undated). Lowering it reduces thinking more reliably than a prompt line does.

**Prompts differ by model.** Prompts for Opus carry no "verify" lines, because verification instructions carried over from older models can cause over-verification ([Opus 5 guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5), undated). Prompts for Sonnet and Haiku carry one line requiring the real check to run, because at low effort they sometimes report a change done without running it ([Sonnet 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5), [Haiku 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-haiku-5-5), both undated). The Opus 5 page advises against subagents that double-check your own work while the Claude Code page recommends a fresh review; this template keeps the fresh review for the reasons above.

**Each rule carries its reason.** The model can then generalise, as in the [prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices) (undated). At most one IMPORTANT per file, because [Claude Code best practices](https://code.claude.com/docs/en/best-practices) (undated) says that if you emphasise many lines none stands out. The files avoid capitals for emphasis.

**CLAUDE.md stays under 60 lines.** Anthropic's [memory page](https://code.claude.com/docs/en/memory) (undated) sets 200 lines as the ceiling because longer files consume context and reduce adherence, and imports do not cut the cost. Sixty is this template's choice: the file is a map, and procedures live in skills, which load when used.

**Scaffolding is re-examined when the model changes.** The [harness post](https://anthropic.com/engineering/harness-design-long-running-apps) (2026-03-24) says each harness component encodes an assumption about what the model cannot do, and found an evaluator became overhead for tasks inside the model's reliable range. So the template ships little and relies on built-ins such as `/init`, plan mode, `/code-review` and worktree isolation.

## Engineering defaults

**Squash-merge one change per pull request** where pull requests exist; solo mode has none. A merge commit is for branches whose internal history matters. A merge queue, when on, sets the method. The host's stack tool handles stacked changes. Sources: [GitHub, merge methods](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github) (undated) says squash drops original authorship and the queue controls the method; [GitHub changelog, 2026-07-30](https://github.blog/changelog/2026-07-30-stacked-pull-requests-are-now-in-public-preview/) announced native stacks in public preview. Stacking is the weakest-sourced area.

**Commit subjects are imperative and about 50 characters.** A type prefix is added only when release tooling reads it, and the repository's own convention wins. Source: [Conventional Commits 1.0.0](https://conventionalcommits.org/en/v1.0.0/) ties types to version bumps.

**Issue-first for small fixes.** The issue holds the problem, the expected behaviour and one check. A spec is written only when an interface, stored data or money changes. Reason: [Böckeler, 2025-10-15](https://www.martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html) calls spec-driven development overkill for small bugs, and [Thoughtworks Radar, 2025-11-05](https://www.thoughtworks.com/en-au/radar/techniques/spec-driven-development) puts it in Assess.

**Schema changes expand and contract.** Additive changes may ship with their code. Drops, renames and new constraints take three steps. Each migration works with the code in production, merges one at a time, and is checked after deploy. Reason: old and new code overlap during a deploy, and the contract step is the one teams skip. Sources: [Fowler, 2014-05-13](https://www.martinfowler.com/bliki/ParallelChange.html), [GitLab post-deployment migrations](https://docs.gitlab.com/ee/development/database/post_deployment_migrations.html) (undated), [Stripe, 2017](https://stripe.com/se/blog/online-migrations). No primary source confirms one migration per deploy, so that part is a judgement from the attribution problem.

**The old path stays behind a flag until the new one passes its gate.** Flags carry an expiry, and rollback means flipping the flag. Data changes cannot be flagged, so they use expand and contract. Sources: [Fowler, 2017-10-09](https://martinfowler.com/articles/feature-toggles.html) advises release toggles last a week or two; [Google SRE Workbook](https://sre.google/workbook/canarying-releases/) (undated) says to run one canary at a time and roll back when the error ratio diverges from control.

**Production access is read-only at the role.** A named question, a time limit, a log line, and no personal fields. Reason: a client-side setting is not enforcement. [Google Cloud, updated 2026-10-22](https://docs.cloud.google.com/iam/docs/temporary-elevated-access) recommends recorded justifications and time-limited grants, and the [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html) (undated) says not to log tokens, passwords or payment data. A reported 2026-04-25 case of an agent deleting a production database ([Mondoo, secondary source](https://mondoo.com/blog/5-lessons-from-9-seconds-ai-agent-deleted-production-database)) shows the cost of an over-privileged token.

**Review depth follows risk.** One approval for routine changes, and a reviewer with domain knowledge for payments, sign-in, personal data and storage. [GitHub code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners) can enforce the second reviewer. Card-handling code may need a non-author reviewer under PCI DSS 6.2.3.1 (confirmed only through secondary pages). No standard sets a reviewer count per risk class.

**A shutdown follows a checklist.** The [GOV.UK retirement guidance](https://www.gov.uk/service-manual/phases/retirement.html) (updated 2025-08-26) covers early notice with the reason and the fate of the data, a redirect, and keeping the domain and certificate for a year. The template adds export while admin access works, a backup with a tested restore, a stop command that holds with a recheck, and a list of what is not backed up. [GDPR Article 20](https://gdpr-info.eu/art-20-gdpr/) gives people a machine-readable export of data held under consent or contract.

## Guards and permissions

**What must hold every time is a hook or a permission rule.** The [features overview](https://code.claude.com/docs/en/features-overview) (undated) says a rule that must hold every time should be a hook, and `CLAUDE.md` is context the model may skip. Hard allow and deny rules belong in permissions, because a hook's `if` filter is best effort ([hooks](https://code.claude.com/docs/en/hooks), undated). Deny rules have gaps (`Bash(rm *)` does not stop `/bin/rm`), so the guard hook adds checks.

**One guard hook with a test file.** It blocks force pushes, `--all` and `--mirror`, destructive resets, `commit -a`, Bash reads of env files, and edits to env files, generated files and migrations that exist on the default branch. It asks the owner for the stack's own deploy and migration commands, listed in `PROD_PATTERNS`, and in the modes other than solo for pushes to or from the default branch. It fails closed when it cannot parse its input. The test file includes false positives such as a commit message that names a blocked command, because a hook that blocks harmless work gets disabled.

**Allow, ask, deny.** Read-only git commands are allowed. Publish and release commands ask in the settings, and the guard asks for deploys, migration applies and, outside solo mode, default-branch pushes. Secret reads and force pushes are denied. Auto mode is a classifier reviewing what no rule settles, and Anthropic reports 0.4 percent false positives and 17 percent false negatives on real overeager actions ([auto mode post](https://www.anthropic.com/engineering/claude-code-auto-mode), 2026-03-25). The false-negative rate is why deny rules and hooks stay. The sandbox is off by default and covers shell commands only ([sandboxing](https://code.claude.com/docs/en/sandboxing), undated).

**Platform challenges stop automation.** A captcha, checkpoint or suspension is a warning, and retrying turns it into a ban. The owner clears it in their own session, and a cooldown follows. A host rate-limit response (HTTP 403 or 429) stops all git and host work for the same reason.

**Personal data has a position before it has a pipeline.** The data position states categories, stores, processors including model vendors, retention and whether people's data is pasted into sessions. Telemetry is scrubbed by allowlist and tested against the production build, because a denylist fails on real servers. Client files stay out of the repository in a git-ignored folder, since a committed file cannot be taken back from every clone.
